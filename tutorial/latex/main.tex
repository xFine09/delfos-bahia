\section*{Introducción}
\addcontentsline{toc}{section}{Introducción}

El presente proyecto documenta el despliegue de un servidor de bases de datos Oracle Database Express Edition (XE) sobre una máquina virtual Ubuntu Server denominada \texttt{delfos.inf}, así como la posterior exportación de los datos a un sistema gestor PostgreSQL.

El trabajo se ha llevado a cabo en paralelo sobre dos equipos anfitriones con distribuciones Linux diferentes: uno con Debian y otro con CachyOS, una distribución basada en Arch Linux. Ambos ejecutan el mismo hipervisor y alojan una máquina virtual idéntica, de modo que el procedimiento dentro del servidor \texttt{delfos.inf} es común. Las diferencias entre ambos entornos se limitan a la preparación del anfitrión y se indican expresamente allí donde aparecen.

El trabajo se ha organizado en apartados que siguen el orden cronológico del despliegue. En cada uno se describen los objetivos, las decisiones técnicas adoptadas y su justificación, los comandos y ficheros de configuración empleados y, por último, las comprobaciones realizadas para verificar el resultado.

Todos los scripts y ficheros de configuración utilizados se encuentran versionados en el repositorio GitHub del proyecto, junto con un registro de las incidencias encontradas durante el proceso y su resolución.

% ==================== APARTADO 1 ====================
\section{Preparación del entorno: VM, Ubuntu Server y arquitectura OFA}

% --------------------------------------------------
\subsection{Objetivos}

El objetivo de este apartado es dejar preparado el servidor sobre el que se instalará Oracle Database XE. Al finalizarlo, el entorno debe cumplir las siguientes condiciones:

\begin{itemize}
    \item Los dos anfitriones, Debian y CachyOS, disponen de Qemu/KVM y libvirt operativos.
    \item La máquina virtual \texttt{delfos.inf} está instalada con Ubuntu Server LTS y es accesible por SSH.
    \item El sistema dispone de una dirección IP fija, un nombre de equipo completo y memoria de intercambio suficiente.
    \item Existen el usuario \texttt{oracle}, sus grupos y la estructura de directorios definida por la arquitectura OFA.
    \item Los parámetros del kernel, los límites de recursos y las variables de entorno cumplen los requisitos de Oracle.
    \item Se dispone de un snapshot de la máquina virtual que permite volver a este estado en caso de error.
\end{itemize}

% --------------------------------------------------

% --------------------------------------------------
\subsection{Requisitos del equipo anfitrión}

La máquina virtual se ejecuta sobre el hipervisor Qemu/KVM, que requiere que el procesador del anfitrión disponga de virtualización por hardware (Intel VT-x o AMD-V) activada en la BIOS. Además, cada anfitrión debe contar con unos 8\,GB de RAM libres, para poder asignar 4\,GB a la máquina virtual, y unos 50\,GB de espacio en disco.

El soporte de virtualización se comprueba con el siguiente comando, válido en ambos anfitriones:

\begin{lstlisting}[language=bash]
grep -Ec '(vmx|svm)' /proc/cpuinfo
\end{lstlisting}

Un resultado mayor que \texttt{0} indica que el procesador admite virtualización. Si el resultado es \texttt{0}, es necesario activarla en la BIOS. Se utiliza \texttt{grep -E} en lugar de \texttt{egrep}, ya que este último está obsoleto y muestra un aviso en las versiones recientes de \texttt{grep}. Cabe señalar que Qemu/KVM no se ejecuta de forma nativa en Windows ni en macOS; en esos casos sería necesario recurrir a una máquina Linux intermedia.

% --------------------------------------------------
\subsection{Instalación del hipervisor Qemu/KVM}

En cada anfitrión se instalan Qemu/KVM y las herramientas de gestión de libvirt con su gestor de paquetes, y se añade el usuario a los grupos \texttt{libvirt} y \texttt{kvm} para que pueda administrar máquinas virtuales sin privilegios de superusuario.

\subsubsection{Anfitrión Debian}

\begin{lstlisting}[language=bash]
sudo apt update
sudo apt install qemu-system-x86 qemu-utils libvirt-daemon-system libvirt-clients virtinst virt-manager
sudo usermod -aG libvirt,kvm $USER
\end{lstlisting}

En Debian, el paquete \texttt{libvirt-daemon-system} habilita e inicia el servicio \texttt{libvirtd} automáticamente. La Figura~\ref{fig:debian-kvm-1} muestra la instalación de los paquetes y la Figura~\ref{fig:debian-kvm-2}, la incorporación del usuario a los grupos.

\begin{figure}[H]

\subsubsection{Anfitrión CachyOS}

\begin{lstlisting}[language=bash]
sudo pacman -S --needed qemu-desktop libvirt virt-install virt-manager dnsmasq
sudo systemctl enable --now libvirtd.service
sudo usermod -aG libvirt,kvm $USER
\end{lstlisting}

A diferencia de Debian, en las distribuciones basadas en Arch los servicios no se activan al instalarlos, por lo que \texttt{libvirtd} se habilita manualmente. El paquete \texttt{dnsmasq} es necesario para que funcione la red NAT por defecto de libvirt, que proporciona DHCP y DNS a las máquinas virtuales.

\subsubsection{Configuración común}

Para que la pertenencia a los nuevos grupos tenga efecto es necesario cerrar sesión y volver a iniciarla.

Por defecto, \texttt{virsh} ejecutado sin \texttt{sudo} se conecta a la instancia de sesión del usuario (\texttt{qemu:///session}) y no a la del sistema, donde se crea la máquina virtual. Para que todos los comandos \texttt{virsh} de este documento actúen sobre la misma instancia, se define la conexión por defecto. La sintaxis depende del intérprete de órdenes de cada anfitrión:

\begin{lstlisting}[language=bash]
# Debian (bash)
echo 'export LIBVIRT_DEFAULT_URI=qemu:///system' >> ~/.bashrc

# CachyOS (fish)
set -Ux LIBVIRT_DEFAULT_URI qemu:///system
\end{lstlisting}

\begin{cabezazo}{\texttt{virsh} no encuentra la máquina virtual}{cab:virsh}
\problema Antes de definir esta variable, \cmd{virsh shutdown delfos} respondía
«error: incorrecto al obtener dominio 'delfos'», aunque la máquina existía.

\causa La máquina se creó con \cmd{virt-install --connect qemu:///system}, pero
\cmd{virsh} sin \cmd{sudo} se conecta a la instancia de sesión del usuario
(\cmd{qemu:///session}), que no la ve.

\solucion Indicar la conexión (\cmd{virsh -c qemu:///system ...}) o fijarla por
defecto con \texttt{LIBVIRT\_DEFAULT\_URI}, como se ha hecho arriba.
\end{cabezazo}

A continuación se activa la red virtual \texttt{default} de libvirt y se marca para que arranque automáticamente. Si ya estaba activa, el primer comando lo indica y puede ignorarse:

\begin{lstlisting}[language=bash]
sudo virsh net-start default
sudo virsh net-autostart default
\end{lstlisting}

Por último, se verifica la instalación en ambos anfitriones:

\begin{lstlisting}[language=bash]
virt-host-validate qemu
systemctl status libvirtd
virsh net-list --all
virsh list --all
\end{lstlisting}

La herramienta \texttt{virt-host-validate}, incluida en libvirt, sustituye a \texttt{kvm-ok}, que forma parte del paquete \texttt{cpu-checker} de Ubuntu y no está disponible en CachyOS. Las comprobaciones \textit{hardware virtualization} y \texttt{/dev/kvm} deben mostrar \texttt{PASS}; los avisos (\texttt{WARN}) relativos a IOMMU o a cifrado de invitados no afectan a este proyecto. El servicio \texttt{libvirtd} debe encontrarse activo y la red \texttt{default}, en estado activo y con inicio automático.

\captura{verificacionlibvirt.png}{Servicio \texttt{libvirtd} activo en el anfitrión CachyOS, con \texttt{dnsmasq} dando servicio a la red \texttt{default}}{fig:libvirt}

% --------------------------------------------------
\subsection{Obtención de Ubuntu Server LTS}

Como sistema operativo del servidor se ha elegido la última versión LTS (\textit{Long Term Support}) de Ubuntu Server en ambos anfitriones, por ofrecer soporte y actualizaciones de seguridad a largo plazo, algo deseable en un servidor de bases de datos. La imagen ISO se descarga desde la web oficial, \url{https://ubuntu.com/download/server}, y se guarda en el directorio \texttt{\textasciitilde/isos/}.

Antes de utilizarla se verifica su integridad, comparando el resumen SHA-256 con el publicado por Canonical:

\begin{lstlisting}[language=bash]
sha256sum ubuntu-*.iso
\end{lstlisting}

Esta comprobación garantiza que la imagen no se ha corrompido durante la descarga ni ha sido alterada. También puede hacerse de forma automática pasando el hash oficial a \texttt{shasum --check}, que responde \texttt{OK} si coincide (Figura~\ref{fig:iso}).

\captura{verificacioniso.png}{Verificación del SHA-256 de \texttt{ubuntu-26.04.1-live-server-amd64.iso}}{fig:iso}

Una vez verificada, la imagen se copia al directorio de imágenes de libvirt. El proceso de Qemu se ejecuta con un usuario propio del sistema que, en CachyOS, no tiene permiso para leer el directorio personal del usuario, de modo que conviene ubicar la ISO en una ruta común a ambos anfitriones:

\begin{lstlisting}[language=bash]
sudo cp ~/isos/ubuntu-26.04-live-server-amd64.iso /var/lib/libvirt/images/
\end{lstlisting}

% --------------------------------------------------
\subsection{Diseño de la red}

Uno de los requisitos del proyecto es poder conectarse al servidor como administrador de forma remota y mediante un cliente Oracle desde otra máquina. Por ello, la elección del modo de red de la máquina virtual condiciona el resto del despliegue. La Tabla~\ref{tab:red} recoge las dos alternativas valoradas.

\begin{table}[!htbp]
    \centering
    \begin{tabularx}{\textwidth}{L{3.5cm} Y Y}
        \toprule
        \textbf{Modo} & \textbf{Ventaja} & \textbf{Inconveniente} \\
        \midrule
        NAT (por defecto en libvirt) & Funciona en cualquier situación, sin configuración adicional. & Solo el anfitrión ve la VM; el acceso desde otras máquinas requiere reenvío de puertos. \\
        \addlinespace
        Puente (\textit{bridge}) & La VM obtiene una IP propia en la red local y es accesible como un equipo más. & No funciona sobre Wi-Fi; requiere conexión cableada. \\
        \bottomrule
    \end{tabularx}
    \caption{Comparativa de los modos de red de la máquina virtual}
    \label{tab:red}
\end{table}

Con NAT, el acceso remoto se consigue reenviando los puertos 22 (SSH) y 1521 (\textit{listener} de Oracle) del anfitrión hacia la máquina virtual mediante reglas de \texttt{iptables} o \texttt{nftables}.

Con el modo puente, en cambio, se crea la interfaz \texttt{br0} en el anfitrión y la máquina virtual queda conectada directamente a la red local. Ninguno de los dos anfitriones utiliza netplan, por lo que el puente se crea con NetworkManager mediante \texttt{nmcli}, disponible por defecto en CachyOS y en Debian con entorno de escritorio. El nombre de la interfaz física (\texttt{enp56s0} en este caso) y el de la conexión cableada original se consultan antes con \texttt{nmcli device} y \texttt{nmcli connection show}:

\begin{lstlisting}[language=bash]
sudo nmcli connection add type bridge ifname br0 con-name br0 bridge.stp no
sudo nmcli connection add type bridge-slave ifname enp56s0 master br0
sudo nmcli connection down "Conexión cableada 1"
sudo nmcli connection up br0
\end{lstlisting}

En un anfitrión Debian sin NetworkManager, el puente se define en \texttt{/etc/network/interfaces}, tras instalar el paquete \texttt{bridge-utils} y eliminar la configuración propia de la interfaz física:

\begin{lstlisting}
auto br0
iface br0 inet dhcp
    bridge_ports enp56s0
    bridge_stp off
\end{lstlisting}

Además, el anfitrión CachyOS tiene \texttt{ufw} activado por defecto, que puede bloquear el tráfico reenviado de las máquinas virtuales en modo NAT. En ese caso se permite el tráfico de la interfaz virtual de libvirt:

\begin{lstlisting}[language=bash]
sudo ufw allow in on virbr0
sudo ufw route allow in on virbr0
sudo ufw route allow out on virbr0
\end{lstlisting}

En nuestro caso se ha optado por el modo \textbf{puente}, ya que el anfitrión está conectado por cable a la red local y así la máquina virtual es accesible directamente desde cualquier equipo de la red, sin reglas de reenvío, lo que simplifica la conexión remota con el cliente Oracle que exige el proyecto. Esta decisión se ha tomado al comienzo del proyecto, puesto que modificar la red una vez configurado el servidor obligaría a rehacer parte de la configuración.

% --------------------------------------------------
\subsection{Creación de la máquina virtual}

La máquina virtual se crea con \texttt{virt-install}, con el mismo comando en ambos anfitriones. El siguiente corresponde a la configuración con el puente \texttt{br0}; en el caso de NAT, la opción \texttt{--network} toma el valor \texttt{network=default}:

\begin{lstlisting}[language=bash]
sudo virt-install \
  --name delfos \
  --memory 4096 \
  --vcpus 2 \
  --cpu host-passthrough \
  --disk size=40,format=qcow2,bus=virtio \
  --cdrom /var/lib/libvirt/images/ubuntu-26.04-live-server-amd64.iso \
  --os-variant ubuntu24.04 \
  --network bridge=br0,model=virtio \
  --graphics spice
\end{lstlisting}

\begin{cabezazo}{\texttt{virt-install}: «No existe el dispositivo» \texttt{br0}}{cab:br0}
\problema La creación de la máquina virtual falla con «No se puede obtener MTU
del interfaz en 'br0': No existe el dispositivo» (Figura~\ref{fig:br0err}).

\causa Primero, el puente \cmd{br0} no existía en el anfitrión. Después de
crearlo con \cmd{nmcli connection add}, el error se repitió porque las conexiones
\cmd{br0} y \cmd{br0-slave} estaban \emph{definidas} pero no \emph{activadas}:
en \cmd{nmcli con show} no tenían dispositivo asociado.

\solucion Activar el puente en una sola orden, para no quedarse sin red a
mitad del cambio, y comprobar con \cmd{ip -br link} que \cmd{br0} existe antes
de repetir \cmd{virt-install} (Figura~\ref{fig:br0ok}):

\begin{lstlisting}[language=bash]
sudo nmcli con down "Conexión cableada 1"; sudo nmcli con up br0-slave; sudo nmcli con up br0
sudo nmcli con modify "Conexión cableada 1" connection.autoconnect no
\end{lstlisting}
\end{cabezazo}

\captura[0.7\textwidth]{cabezazovirt.png}{\texttt{virt-install} falla porque \texttt{br0} no existe}{fig:br0err}
\captura{solcabezazovirt.png}{Con el puente activado, \texttt{virt-install} crea el dominio y abre la consola}{fig:br0ok}

Los recursos asignados se justifican de la siguiente manera:

\begin{itemize}
    \item \textbf{Memoria (4\,GB) y CPU (2 núcleos):} Oracle XE limita su instancia a un máximo de 2 CPU y 2\,GB de RAM, por lo que estos valores cubren sus necesidades y dejan margen al sistema operativo.
    \item \textbf{Disco (40\,GB, formato qcow2):} el software de Oracle XE ocupa entre 6 y 7\,GB, y la base de datos y los ficheros de log crecen con el uso. El formato qcow2 reserva el espacio de forma dinámica y permite crear snapshots.
    \item \textbf{Controladores virtio:} tanto el disco como la interfaz de red usan controladores paravirtualizados, que ofrecen mejor rendimiento que los dispositivos emulados.
\end{itemize}

Los valores admitidos por \texttt{--os-variant} dependen de la base de datos \texttt{osinfo-db} instalada, que suele ser más reciente en CachyOS que en Debian. Si la versión de Ubuntu no figura en la lista, que se consulta con \texttt{virt-install --osinfo list}, se utiliza la versión más próxima.

% --------------------------------------------------
\subsection{Instalación de Ubuntu Server}

Durante la instalación del sistema operativo se seleccionaron las siguientes opciones:

\begin{itemize}
    \item \textbf{Idioma y teclado:} español.
    \item \textbf{Tipo de instalación:} Ubuntu Server estándar, no minimizada, para disponer de las herramientas habituales de administración.
    \item \textbf{Red:} configuración por DHCP; la IP fija se establece tras la instalación.
    \item \textbf{Almacenamiento:} disco completo con LVM y los valores por defecto, lo que facilita ampliar los volúmenes más adelante. Conviene observar que, por defecto, el instalador solo asigna 19\,GB al volumen raíz y deja otros 19\,GB libres en el grupo de volúmenes (Figura~\ref{fig:disco}); esto provocó el cabezazo~\ref{cab:disco} del Apartado~\ref{sec:apartado2}.
    \item \textbf{Perfil:} nombre de equipo \texttt{delfos} y un usuario administrador (\texttt{sercal}). Las credenciales se custodian en un gestor de contraseñas y no se incluyen en el repositorio.
    \item \textbf{SSH:} se instala el servidor OpenSSH para la administración remota.
    \item \textbf{Paquetes adicionales:} no se instala ningún snap adicional, para mantener el sistema lo más limpio posible.
\end{itemize}

\subsubsection{Dirección IP fija}

Un servidor de bases de datos debe mantener siempre la misma dirección, ya que los clientes se conectan a ella. Para fijarla se edita el fichero de netplan, que se encuentra en \texttt{/etc/netplan/}. Su nombre puede variar; en nuestro caso es \texttt{00-installer-config.yaml}:

\begin{lstlisting}
network:
  version: 2
  ethernets:
    enp1s0:
      dhcp4: false
      addresses: [192.168.3.133/24]
      routes:
        - to: default
          via: 192.168.3.1
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8]
\end{lstlisting}

El fichero generado por el instalador incluye además un bloque \texttt{match} por dirección MAC con \texttt{set-name}, que se conserva tal cual. Antes de editarlo se consulta la red actual con \texttt{ip -br a} e \texttt{ip route} y se guarda una copia de seguridad (Figura~\ref{fig:netplanprev}).

\captura[0.8\textwidth]{ipfija.png}{Configuración DHCP original, dirección y puerta de enlace actuales, y copia de seguridad}{fig:netplanprev}

Los cambios se aplican con \texttt{sudo netplan try}, que revierte la configuración automáticamente a los 120 segundos si no se confirma, de modo que un error no deja la máquina incomunicada. Una vez comprobado, la configuración queda aplicada de forma permanente. La dirección elegida está libre en la red y fuera del rango que reparte el servidor DHCP del router, para evitar conflictos. Si cada miembro del grupo trabaja en una red distinta, la dirección, la puerta de enlace y la máscara se adaptan a la red de cada anfitrión.

\begin{cabezazo}{\texttt{netplan try} revierte la IP fija}{cab:netplan}
\problema Tras el primer \cmd{sudo netplan try} la máquina pierde la conexión y
netplan termina con «Reverting» (Figura~\ref{fig:netplanrev}).

\causa Se copió una configuración de ejemplo con la dirección
\cmd{192.168.1.50/24} y la puerta de enlace \cmd{192.168.1.1}
(Figura~\ref{fig:netplanmal}), pero la red real es \cmd{192.168.3.0/24}, con
puerta de enlace \cmd{192.168.3.1}.

\solucion Usar los valores reales obtenidos con \cmd{ip -br a} e
\cmd{ip route | grep default}: \cmd{192.168.3.133/24} y \cmd{192.168.3.1}
(Figura~\ref{fig:netplanok}). Gracias a \cmd{netplan try}, el error se
deshizo solo sin necesidad de acceder por consola.
\end{cabezazo}

\captura[0.45\textwidth]{netplanconfig.png}{Configuración errónea: dirección y puerta de enlace de otra red}{fig:netplanmal}

\captura[0.45\textwidth]{cabezazoipsol.png}{Configuración correcta de la IP fija}{fig:netplanok}

\subsubsection{Memoria de intercambio}

Oracle requiere al menos 2\,GB de memoria de intercambio. Tras comprobar el espacio disponible con \texttt{free -h}, y al ser inferior a ese valor, se crea un fichero de intercambio y se registra en \texttt{/etc/fstab} para que se active en cada arranque:

\begin{lstlisting}[language=bash]
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
\end{lstlisting}

\subsection{Preparación de la arquitectura OFA}

OFA (\textit{Optimal Flexible Architecture}) es el estándar de Oracle para organizar los usuarios, los grupos y los directorios de una instalación, con el fin de facilitar su mantenimiento y la convivencia de varias versiones. En las distribuciones soportadas oficialmente, Oracle proporciona un paquete \textit{preinstall} que realiza esta preparación de forma automática; al no existir para Ubuntu, se ha llevado a cabo manualmente.

\begin{cabezazo}{No existe el paquete \textit{preinstall} para Ubuntu}{cab:preinstall}
\problema Ubuntu no dispone de \cmd{oracle-database-preinstall-21c}, y el
directorio \cmd{/etc/sysctl.d} solo contiene un \cmd{README.sysctl}.

\causa Oracle solo publica ese paquete para Oracle Linux y Red Hat.

\solucion Crear a mano todo lo que el paquete haría: grupos, usuario
\cmd{oracle}, directorios OFA, \cmd{/etc/sysctl.d/99-oracle.conf},
\cmd{/etc/security/limits.d/oracle.conf} y variables de entorno, como se
describe a continuación.
\end{cabezazo}

\subsubsection{Grupos y usuario}

Se crean los grupos del sistema que define Oracle (\texttt{oinstall} para la instalación, \texttt{dba} para la administración y \texttt{oper} para las operaciones básicas) y el usuario \texttt{oracle}, propietario del software:

\begin{lstlisting}[language=bash]
sudo groupadd -g 54321 oinstall
sudo groupadd -g 54322 dba
sudo groupadd -g 54323 oper
sudo useradd -u 54321 -g oinstall -G dba,oper -m -s /bin/bash oracle
sudo passwd oracle
\end{lstlisting}

Se utilizan los identificadores 54321--54323, que son los que Oracle emplea por defecto en sus propios sistemas.

\subsection{Snapshot del estado preparado}

Con el sistema ya preparado y antes de instalar Oracle, se crea un snapshot de la máquina virtual. De este modo, si se produce algún error durante la instalación, es posible restaurar este estado en lugar de repetir todo el proceso. El snapshot se crea desde el anfitrión con la máquina apagada; los comandos son los mismos en Debian y en CachyOS gracias a la variable \texttt{LIBVIRT\_DEFAULT\_URI} definida anteriormente:

\begin{lstlisting}[language=bash]
virsh shutdown delfos
virsh snapshot-create-as delfos --name "s1-preparada-pre-oracle" --description "Ubuntu + OFA, sin Oracle"
virsh snapshot-list delfos
\end{lstlisting}

En caso necesario, la restauración se realiza con:

\begin{lstlisting}[language=bash]
virsh snapshot-revert delfos s1-preparada-pre-oracle
\end{lstlisting}

Dado que se trata de snapshots internos del formato qcow2, no deben combinarse con copias manuales del fichero de disco, ya que podrían quedar en un estado inconsistente.

\subsection{Conversión del RPM a paquete Debian}
\label{sec:alien}

Ubuntu usa paquetes \cmd{.deb}, así que el RPM se convierte con \cmd{alien}
conservando los scripts de instalación (\cmd{--scripts}):

\begin{lstlisting}[style=bash]
sudo alien --scripts -d oracle-database-xe-21c-1.0-1.ol8.x86_64.rpm
\end{lstlisting}

Los avisos \cmd{NOKEY} que aparecen repetidos solo indican que la clave GPG de
Oracle no está importada en el sistema; no son errores.

\captura{alien.png}{Primer intento de conversión con \texttt{alien}}{fig:alien}

La conversión resultó ser el paso más delicado por falta de espacio, primero en
el disco y después en \cmd{/tmp}.

\begin{cabezazo}{\texttt{alien} falla con «No space left on device»}{cab:disco}
\problema La conversión aborta copiando las librerías de
\cmd{dbhomeXE/lib} con \cmd{cp: error copying ... No space left on device} y
\cmd{make: *** [debian/rules:7: binary] Error 2}.

\causa \cmd{alien} descomprime el RPM y lo vuelve a copiar a
\cmd{debian/} antes de empaquetar, por lo que necesita unos 20 GB libres. El
instalador de Ubuntu Server solo asignó 19 GB al volumen lógico raíz
(\cmd{ubuntu-lv}) y dejó otros 19 GB libres en el grupo de volúmenes:

\begin{lstlisting}[style=fichero]
/dev/mapper/ubuntu--vg-ubuntu--lv   19G  9,6G  8,0G  55% /
  VG        #PV #LV #SN Attr   VSize   VFree
  ubuntu-vg   1   1   0 wz--n- <38,00g 19,00g
\end{lstlisting}

\solucion Primero se asigna al volumen raíz el espacio libre del grupo y,
para tener margen para la base de datos, se amplía además el disco virtual en
30 GB desde el anfitrión:

\begin{lstlisting}[style=bash]
# En la VM: usar el espacio libre del VG
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv

# En el anfitrión, con la VM apagada: ampliar el qcow2
sudo qemu-img resize /var/lib/libvirt/images/delfos.qcow2 +30G

# En la VM: crecer partición, volumen físico y volumen lógico
sudo apt install -y cloud-guest-utils
sudo growpart /dev/vda 3
sudo pvresize /dev/vda3
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
df -h /
\end{lstlisting}

El sistema de ficheros raíz pasa a 67 GB con 55 GB libres
(figuras~\ref{fig:qemuimg} y~\ref{fig:lvextend}).
\end{cabezazo}

\captura[0.6\linewidth]{cabezazoalien.png}{Ampliación del disco virtual con \texttt{qemu-img resize}}{fig:qemuimg}

\captura{solucioncabezazoalien.png}{\texttt{growpart}, \texttt{pvresize} y \texttt{lvextend}: el volumen raíz pasa de 38 a 68 GiB}{fig:lvextend}

\begin{cabezazo}{\texttt{zstd write error} con 55 GB libres}{cab:tmpfs}
\problema Con espacio de sobra en el disco, \cmd{alien} vuelve a fallar al
final con \cmd{dpkg-deb (subproceso): comprimiendo miembro tar: zstd write
error: No space left on device}, y el \cmd{.deb} generado pesa solo 521 KB.

\causa \cmd{dpkg-deb} comprime el paquete en un fichero temporal en
\cmd{/tmp}, y en Ubuntu 26.04 \cmd{/tmp} es un \emph{tmpfs} en memoria RAM de
solo 1,7 GB (la mitad de la RAM de la VM):

\begin{lstlisting}[style=fichero]
$ df -h /tmp
Filesystem      Size  Used Avail Use% Mounted on
tmpfs           1,7G     0  1,7G   0% /tmp
\end{lstlisting}

\solucion Indicar un directorio temporal en disco con la variable
\cmd{TMPDIR}. Se usa \cmd{sudo env} porque \cmd{sudo} descarta las variables de
entorno del usuario:

\begin{lstlisting}[style=bash]
mkdir -p ~/tmp-alien
sudo env TMPDIR=/home/sercal/tmp-alien alien --scripts -d \
     oracle-database-xe-21c-1.0-1.ol8.x86_64.rpm
ls -lh *.deb
\end{lstlisting}

Los numerosos mensajes \cmd{dpkg-shlibdeps: error: cannot find library ...}
que aparecen durante la conversión no son el problema: \cmd{alien} los ignora
(\cmd{Error 25 (ignored)}) porque son librerías que Oracle incluye en su propio
\texttt{ORACLE\_HOME}.
\end{cabezazo}

\captura{debcreado.png}{Paquete \texttt{oracle-database-xe-21c\_1.0-2\_amd64.deb} generado correctamente (2,2 GB)}{fig:deb}

\subsection{Instalación del paquete}
\label{sec:dpkg}

Antes de instalar se crea el enlace que Oracle espera para \cmd{libaio}
(en Ubuntu 26.04 la librería se llama \cmd{libaio.so.1t64}) y se comprueba que
el \texttt{ORACLE\_BASE} pertenece al usuario \cmd{oracle}:

\begin{lstlisting}[style=bash]
sudo ln -sf /usr/lib/x86_64-linux-gnu/libaio.so.1t64 \
            /usr/lib/x86_64-linux-gnu/libaio.so.1
sudo chown oracle:oinstall /opt/oracle /opt/oraInventory
sudo dpkg -i oracle-database-xe-21c_1.0-2_amd64.deb
\end{lstlisting}

\begin{cabezazo}{\texttt{awk: command not found} en el script de preinstalación}{cab:awk}
\problema \cmd{dpkg -i} se detiene en el \emph{preinst}:
\cmd{/var/lib/dpkg/tmp.ci/preinst: line 188: awk: command not found}.

\causa Siguiendo una receta pensada para distribuciones antiguas se ejecutó
\cmd{sudo ln -sf /usr/bin/awk /bin/awk}. En Ubuntu moderno \cmd{/bin} es un
enlace a \cmd{/usr/bin} (\emph{usrmerge}), así que el comando sobrescribió
\cmd{/usr/bin/awk} con un enlace que apunta a sí mismo
(\cmd{/usr/bin/awk -> /usr/bin/awk}) y \cmd{awk} dejó de existir en todo el
sistema.

\solucion Borrar el enlace roto y reinstalar \cmd{mawk}, que regenera el
grupo de alternativas de \cmd{awk}:

\begin{lstlisting}[style=bash]
sudo rm /usr/bin/awk
sudo apt install --reinstall mawk
ls -l /usr/bin/awk      # /usr/bin/awk -> /etc/alternatives/awk
awk --version
\end{lstlisting}

El aviso \cmd{ln: failed to create symbolic link '/bin/awk': Already exists}
que muestra después el instalador de Oracle es inofensivo.
\textbf{No hay que crear ningún enlace para \cmd{awk} en Ubuntu.}
\end{cabezazo}

\captura{cabezazoawk.png}{El enlace circular de \texttt{awk} y su reparación reinstalando \texttt{mawk}}{fig:awk}

\begin{cabezazo}{\texttt{ORACLE\_BASE} no pertenece al usuario \texttt{oracle}}{cab:oraclebase}
\problema En la misma ejecución, el preinstalador muestra
\cmd{[SEVERE] The install cannot proceed because ORACLE_BASE directory
(/opt/oracle) is not owned by "oracle" user}.

\causa El paquete comprueba la propiedad de \cmd{/opt/oracle} antes de
desempaquetar (y lo hace usando \cmd{awk}, por lo que el problema anterior
agravaba este).

\solucion \cmd{sudo chown -R oracle:oinstall /opt/oracle /opt/oraInventory}
\emph{antes} de instalar. Una vez instalado Oracle \textbf{no debe repetirse el
\cmd{chown -R}}: ver el cabezazo~\ref{cab:oradism}.
\end{cabezazo}

Con \cmd{awk} reparado, la instalación termina correctamente:

\captura{solawk.png}{\texttt{Oracle home installed successfully and ready to be configured}}{fig:dpkgok}

El instalador sugiere ejecutar \cmd{/etc/init.d/oracle-xe-21c configure}, pero
\textbf{no se ejecuta}: ese script crearía una base de datos \cmd{XE} con valores
por defecto, mientras que BAHIA debe crearse con DBCA y los parámetros del
enunciado.

Se toma una instantánea de la VM en este punto y se borran los paquetes
descargados (los originales se conservan en el directorio \cmd{software/} del
anfitrión):

\begin{lstlisting}[style=bash]
# Anfitrión, con la VM apagada
virsh -c qemu:///system snapshot-create-as delfos --name "s2-xe-instalado" \
      --description "Oracle XE 21c instalado, sin BAHIA"
# VM
rm -f ~/oracle-database-xe-21c-1.0-1.ol8.x86_64.rpm
sudo rm -f ~/oracle-database-xe-21c_1.0-2_amd64.deb
\end{lstlisting}

\subsection{Creación de BAHIA.inf con DBCA}
\label{sec:dbca}

\subsubsection{Intento con la interfaz gráfica}

La máquina es un Ubuntu Server sin entorno gráfico, así que la idea era lanzar
DBCA reenviando su ventana al escritorio del anfitrión por SSH (X11
\emph{forwarding}). Se instalaron las dependencias gráficas mínimas en la VM:

\begin{lstlisting}[style=bash]
sudo apt install -y xauth libxrender1 libxtst6 libxi6 fontconfig
\end{lstlisting}

\captura{x11.png}{Dependencias para el reenvío X11}{fig:x11deps}

\begin{cabezazo}{DBCA: «DISPLAY not set»}{cab:display}
\problema Al ejecutar \cmd{dbca} tras \cmd{sudo su - oracle} aparece
\cmd{DISPLAY not set. Set DISPLAY environment variable, then re-run.}

\causa La variable \cmd{DISPLAY} solo la crea una conexión \cmd{ssh -X} o
\cmd{ssh -Y} hecha desde el anfitrión gráfico; una sesión abierta con
\cmd{su} desde la consola de la VM no tiene pantalla a la que enviar la
ventana. Además, al pegar de golpe un bloque que empieza por
\cmd{sudo su - oracle}, las líneas siguientes se pierden mientras \cmd{sudo}
pide la contraseña.

\solucion Conectarse con \cmd{ssh -Y oracle@delfos.inf} desde el escritorio
del anfitrión, o copiar la \emph{cookie} X11 de \cmd{sercal} a \cmd{oracle}
(\cmd{xauth list $DISPLAY} / \cmd{xauth add ...}) ejecutando las órdenes de una
en una.
\end{cabezazo}

\begin{cabezazo}{DBCA: «Invalid MIT-MAGIC-COOKIE-1 key»}{cab:cookie}
\problema Con \cmd{DISPLAY=localhost:11.0} y la \emph{cookie} correctamente
copiada (aparece en \cmd{xauth list}), DBCA falla con
\cmd{Invalid MIT-MAGIC-COOKIE-1 key} y
\cmd{java.lang.NoClassDefFoundError: Could not initialize class
sun.awt.X11.XToolkit}.

\causa El rechazo viene del lado del anfitrión: al conectar, SSH avisa
\cmd{Warning: No xauth data; using fake authentication data for X11
forwarding}. El escritorio del anfitrión (Wayland/XWayland) no ofrece una
\emph{cookie} X11 válida, así que la que llega a la VM es falsa y el servidor
gráfico rechaza la ventana, tanto con \cmd{-X} como con \cmd{-Y}.

\solucion Se abandona la interfaz gráfica y se usa DBCA en \textbf{modo
silencioso} (\cmd{-silent}), que ofrece las mismas opciones, incluida la
generación de los scripts de creación, y queda mejor documentado en el
repositorio (\cmd{scripts/03-dbca-bahia.sh}).
\end{cabezazo}

\captura[0.75\linewidth]{cabezazox11.png}{«No xauth data; using fake authentication data» al conectar con \texttt{ssh -Y}}{fig:x11a}
\captura[0.75\linewidth]{cabezazox11_2.png}{La \emph{cookie} de \texttt{sercal} y el bloque pegado que se pierde tras \texttt{sudo su}}{fig:x11b}

\subsubsection{Generación de los scripts de creación}

El enunciado pide activar la opción de DBCA que genera los ficheros de comandos
de creación. En modo silencioso es la operación \cmd{-generateScripts}. Primero
se comprueba el nombre de la plantilla de XE:

\begin{lstlisting}[style=bash]
ls $ORACLE_HOME/assistants/dbca/templates/
# XE_Database.dbc  XE_Seed_Database.ctl  XE_Seed_Database.dfb  pdbseed.dfb  pdbseed.xml
mkdir -p /opt/oracle/admin/BAHIA/scripts
\end{lstlisting}

\begin{lstlisting}[style=bash]
dbca -silent -generateScripts \
  -templateName XE_Database.dbc \
  -gdbName BAHIA.inf -sid XE \
  -characterSet AL32UTF8 -nationalCharacterSet AL16UTF16 \
  -createAsContainerDatabase true -numberOfPDBs 1 -pdbName BAHIAPDB \
  -datafileDestination /opt/oracle/oradata -storageType FS \
  -memoryMgmtType AUTO_SGA -totalMemory 1536 \
  -emConfiguration NONE \
  -scriptDest /opt/oracle/admin/BAHIA/scripts
\end{lstlisting}

El tamaño de bloque no se indica porque la plantilla de XE lo fija en 8192 bytes,
justo el valor que pide el enunciado.

\begin{cabezazo}{\texttt{[DBT-12513]} Esquemas de ejemplo no soportados}{cab:dbt12513}
\problema Con la opción \cmd{-sampleSchema true}, DBCA responde
\texttt{[FATAL] [DBT-12513] El esquema de muestra no está soportado en la versión
del directorio raíz de Oracle 21.0.0.0.0.}

\causa Desde Oracle 21c, DBCA ya no incluye los esquemas de ejemplo; Oracle
los publica aparte en GitHub (\cmd{oracle-samples/db-sample-schemas}).

\solucion Crear la base de datos sin \cmd{-sampleSchema} e instalar los
esquemas después desde el repositorio oficial (sección~\ref{sec:hr}).
\end{cabezazo}

\begin{cabezazo}{\texttt{-generateScripts} termina con \texttt{NullPointerException}}{cab:npe}
\problema Tras mostrar todos los porcentajes hasta el 100\,\%, el comando
acaba con \cmd{[FATAL] java.lang.NullPointerException}. Parecía que la base de
datos podía haberse creado a medias.

\causa Es un fallo de DBCA al terminar la generación de scripts en modo
silencioso. El progreso es simulado: en el log todos los pasos ocurren en el
mismo segundo (20:47:51), no hay proceso \cmd{pmon}, \cmd{/opt/oracle/oradata}
está vacío y \cmd{/etc/oratab} no tiene entradas.

\solucion Ninguna: los 17 scripts se generan completos en
\cmd{/opt/oracle/admin/BAHIA/scripts}. Se verifican y se continúa con
\cmd{-createDatabase}.
\end{cabezazo}

\subsubsection{Creación de la base de datos}

La creación se lanza dentro de \cmd{tmux} para que no se interrumpa si se corta
la conexión SSH. DBCA pide por teclado las contraseñas de \cmd{SYS},
\cmd{SYSTEM} y \cmd{PDBADMIN}, de modo que no quedan en el historial:

\begin{lstlisting}[style=bash]
dbca -silent -createDatabase \
  -templateName XE_Database.dbc \
  -gdbName BAHIA.inf -sid XE \
  -characterSet AL32UTF8 -nationalCharacterSet AL16UTF16 \
  -createAsContainerDatabase true -numberOfPDBs 1 -pdbName BAHIAPDB \
  -datafileDestination /opt/oracle/oradata -storageType FS \
  -memoryMgmtType AUTO_SGA -totalMemory 1536 \
  -emConfiguration NONE
\end{lstlisting}

\begin{cabezazo}{\texttt{[DBT-10011]} Permisos incorrectos de \texttt{oradism}}{cab:oradism}
\problema La creación se detiene con
\cmd{[FATAL] [DBT-10011] Se han detectado una propiedad o permisos incorrectos
para el archivo (/opt/oracle/product/21c/dbhomeXE/bin/oradism)}, acompañado de
\cmd{PRVG-11960} (falta el bit SUID) y \cmd{PRVG-2031} (se esperaba
\cmd{root(0)} y se encontró \cmd{oracle(54321)}).

\causa \cmd{oradism} gestiona la memoria compartida de la instancia y debe
pertenecer a \cmd{root} con el bit SUID. Los \cmd{chown -R oracle:oinstall
/opt/oracle} ejecutados tras la instalación le cambiaron el propietario y le
quitaron ese bit.

\solucion Ejecutar como \cmd{root} el script \cmd{root.sh} del
\texttt{ORACLE\_HOME}, que restablece los permisos especiales:

\begin{lstlisting}[style=bash]
sudo /opt/oracle/product/21c/dbhomeXE/root.sh
ls -l /opt/oracle/product/21c/dbhomeXE/bin/oradism
# -rwsr-x--- 1 root oinstall 1867560 Aug 18  2021 .../oradism
\end{lstlisting}

\cmd{root.sh} deja su salida en un log que \cmd{sercal} solo puede leer con
\cmd{sudo} (de ahí un \cmd{Permission denied} al hacer \cmd{cat} sin él).
\textbf{A partir de aquí no se vuelve a usar \cmd{chown -R} sobre
\cmd{/opt/oracle}.}
\end{cabezazo}

\begin{cabezazo}{\texttt{[DBT-06208]} Contraseñas débiles}{cab:pwd}
\problema DBCA muestra un aviso \cmd{DBT-06208} para \cmd{SYS},
\cmd{SYSTEM} y \cmd{PDBADMIN}.

\causa Oracle recomienda al menos 8 caracteres con mayúsculas, minúsculas y
dígitos, y desaconseja palabras como «oracle». Es un aviso, no un error.

\solucion Usar contraseñas robustas, ya que en la fase siguiente se abrirá
el puerto 1521 a la red para la conexión remota como administrador. Las
contraseñas se guardan en un gestor de contraseñas, nunca en el repositorio.
\end{cabezazo}

\subsection{Arranque automático}
\label{sec:arranque}

El paquete RPM de Oracle no crea en Ubuntu un servicio de arranque, así que se
define uno para \cmd{systemd} basado en las utilidades \cmd{dbstart} y
\cmd{dbshut}, que arrancan y detienen las instancias marcadas con \cmd{Y} en
\cmd{/etc/oratab} (y también el listener, al recibir el \texttt{ORACLE\_HOME}).

\begin{lstlisting}[style=bash]
sudo sed -i 's|^XE:/opt/oracle/product/21c/dbhomeXE:N|XE:/opt/oracle/product/21c/dbhomeXE:Y|' /etc/oratab
grep XE /etc/oratab
\end{lstlisting}

\captura[0.8\linewidth]{arranqueauto.png}{Activación del arranque automático en \texttt{/etc/oratab}}{fig:oratab}

\begin{lstlisting}[style=fichero,caption={\texttt{/etc/systemd/system/oracle-xe.service}}]
[Unit]
Description=Oracle Database XE 21c (BAHIA.inf) y listener
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
User=oracle
Group=oinstall
Environment=ORACLE_HOME=/opt/oracle/product/21c/dbhomeXE
ExecStart=/opt/oracle/product/21c/dbhomeXE/bin/dbstart /opt/oracle/product/21c/dbhomeXE
ExecStop=/opt/oracle/product/21c/dbhomeXE/bin/dbshut /opt/oracle/product/21c/dbhomeXE
TimeoutSec=600

[Install]
WantedBy=multi-user.target
\end{lstlisting}

\begin{cabezazo}{«I'm sorry oracle. I'm afraid I can't do that»}{cab:sudo}
\problema Al ejecutar \cmd{sudo systemctl ...} desde la sesión del usuario
\cmd{oracle}, \cmd{sudo} lo rechaza y el servicio queda \cmd{disabled} e
\cmd{inactive (dead)}.

\causa El usuario \cmd{oracle} no pertenece al grupo \cmd{sudo}, y es lo
correcto: el propietario del software de Oracle no debe tener privilegios de
administración.

\solucion Cambiar al usuario administrador (\cmd{su - sercal}) y activar el
servicio desde ahí.
\end{cabezazo}

Antes de activarlo se detienen la base de datos y el listener arrancados a mano:

\captura[0.7\linewidth]{servicio2.png}{Parada manual previa a la activación del servicio}{fig:stopmanual}

\begin{lstlisting}[style=bash]
sudo systemctl daemon-reload
sudo systemctl enable --now oracle-xe
systemctl status oracle-xe
\end{lstlisting}

\captura{service3.png}{Servicio \texttt{enabled} y \texttt{active (exited)}: listener y procesos de la instancia \texttt{XE}}{fig:service}

La prueba definitiva es reiniciar la máquina y comprobar que todo vuelve solo,
incluida la PDB gracias al \cmd{SAVE STATE}:

\begin{lstlisting}[style=bash]
sudo reboot
# tras volver a entrar como sercal
systemctl status oracle-xe
ps -ef | grep [p]mon
sudo su - oracle -c 'echo "SHOW PDBS" | sqlplus -s / as sysdba'
\end{lstlisting}

\captura{servicecheck1.png}{Tras el reinicio, el servicio ha arrancado solo}{fig:reboot1}
\captura[0.85\linewidth]{servicecheck2.png}{Proceso \texttt{xe\_pmon\_XE} activo y \texttt{BAHIAPDB} en \texttt{READ WRITE} sin intervención manual}{fig:reboot2}

\subsection*{Lecciones aprendidas}

\begin{itemize}
  \item Comprobar el espacio \emph{real} disponible (\cmd{df -h /}, \cmd{vgs},
        \cmd{df -h /tmp}) antes de procesar paquetes grandes.
  \item No aplicar a ciegas recetas escritas para distribuciones antiguas: en
        Ubuntu moderno \cmd{/bin} y \cmd{/usr/bin} son el mismo directorio.
  \item No usar \cmd{chown -R} sobre un \texttt{ORACLE\_HOME} ya instalado: hay
        binarios que deben ser de \cmd{root} con SUID.
  \item En una CDB, los esquemas de aplicación van siempre en una PDB.
  \item Separar los usuarios: \cmd{sercal} administra el sistema y \cmd{oracle}
        administra la base de datos.
  \item Hacer instantáneas antes de cada paso delicado ha permitido trabajar sin
        miedo a tener que reinstalar desde cero.
\end{itemize}
